# Release process

No release is valid merely because it compiles or has a tag. Publication is a
separate, owner-approved operation performed only after the gates below pass on
the exact candidate commit.

`docs/production-readiness.json` is the machine-checked gate ledger for the
standalone beta, standalone production, and PFI production claims. CTest rejects
unknown states, duplicate gates, missing evidence paths, an unfrozen candidate
with a commit, a frozen candidate without an exact commit, or any `READY` claim
while a required gate is not `PASS`. The ledger records evidence; it does not
grant publication authority or replace the checks below.

## Candidate gate

1. Review `docs/support-profile-0.1.0.json`, which classifies every conformance
   row exactly once and excludes both the viewer and PFI adapter from the
   standalone library boundary. Change its state from `PREPARED` to `FROZEN`
   and bind the exact candidate commit only after the claimed dispositions are
   final. Every required row has a fixture or is explicitly marked
   `LIMITED`/`NOT_TESTED`; synthetic and native evidence remain distinguishable.
2. Require the full Linux/macOS/Windows static and shared installed-package CI
   matrix, sanitizer tests, deterministic mutation smoke, and coverage-guided
   fuzz job on the candidate commit.
3. Re-run independent-producer and independent-consumer oracles. Record exact
   versions, fixture/file hashes, expected pixels/metadata, and limitations.
4. Complete native PixInsight acceptance for claimed PFI profiles without UI
   automation, and record PFI adapter parity plus the tested rollback switch.
5. Review the public API, error/resource contracts, threat model, dependency
   notices, SPDX SBOM, and security-reporting channel. No unresolved high
   severity issue may be waived into a production claim.
6. Measure representative mono/RGB memory and throughput on supported hosts.
   Local observations are not portable SLAs.
7. Verify the deterministic source artifact and SHA-256 generated by CI.

The CI and local rehearsal share `cmake/PrepareSourceCandidate.cmake`. It only
packages a clean checked-out `HEAD`, refuses an existing output directory,
requires two generated archives to be byte-identical, and writes the full
commit, version, archive name/size/SHA-256, prefix, determinism result, and
`publicationAuthorized: false` to `source-candidate.json`. Preparing this
manifest never creates a tag or authorizes publication.

The preparation mechanism has a retained clean-room rehearsal on exact commit
`75b1cc588254d01f801efe4de597a9b66a1347f1`: the archive was extracted outside
the repository, built with warnings as errors, tested, installed, and consumed
through only its installed CMake package. This validates the packaging path,
not a future frozen candidate or final release asset.

## Version and artifact gate

Before tagging, update and cross-check the version in `CMakeLists.txt`,
`src/version.cpp`, package tests, and `sbom/source-dependencies.spdx.json`.
Regenerate any versioned documentation and rerun the complete candidate gate.

The intended release assets are:

- deterministic source archive and SHA-256;
- source-dependency SPDX SBOM plus resolved binary SBOMs where applicable;
- release notes with supported/unsupported conformance rows and security fixes;
- a separately signed/notarized macOS viewer bundle when the viewer is included.

The installed CMake package carries the support profile, conformance matrix,
and pinned specification provenance in addition to the license/notice files and
SBOMs. Its package-consumer gate verifies that these files are relocatable,
mutually bound by SHA-256, and keep the viewer outside the library contract.

The viewer PoC is not silently promoted to a library support claim. Unsigned or
ad-hoc-signed local bundles remain development artifacts.

## Publication and rollback

Record the exact repository, branch, full commit, proposed annotated tag,
release title, and asset hashes before requesting publication approval. Push
the tag and create the release only after explicit approval.

After publication, verify the remote tag target, download each asset, recompute
its hash, and run the installed-package consumer. If any identity or gate is
wrong, stop distribution, document the discrepancy, and issue a corrected new
version; do not move a public release tag.
